# 일일 운영 매뉴얼 (자동 실행용)

Orca 자동화 "name-that-llm 일일 운영"(id 9a4cdb35-e955-4066-89d1-7d2e45c78f3b, kaggle 워크스페이스, 매일 09:10과 21:10 KST)이 이 문서를 따르라는 지시로 Claude를 실행한다. 사용자는 Orca 실행 기록으로 모니터링한다. (예전 launchd 방식은 2026-11-05에 해제함. `scripts/daily-ntl.sh`는 수동 실행용으로만 남김)
Kaggle 제출 한도(하루 5회)는 00:00 UTC = 09:00 KST에 초기화된다. 채점은 무거운 파이프라인 약 8시간, 경량 노트북 수십 분.

## 절대 규칙
- **무료 자원만** 사용: Kaggle 무료 GPU/CPU 노트북, 로컬 맥. 유료 API·클라우드 GPU 금지.
- **솔로 참가**: 팀 병합 제안이나 수락 금지. 디스커션에 글 쓰기 금지. 공개 노트북 publish 금지 (모든 커널은 `is_private: true`).
- **다른 작업 건드리지 않기**: `casmi26-*`, `arc26-*` 등 다른 대회 커널은 중지하거나 수정하지 않는다. GPU 세션 2개 한도에 걸리면 기다리거나 CPU 커널로 대신한다.
- **하루 제출 5회 이하**. 제출은 반드시 commit이 성공했고, (GPU 임베딩 등) 로컬과 Kaggle 결과가 일치하는지 확인한 커널 버전만.
- 데이터, 모델, 출력은 git에 넣지 않는다. 커밋은 하지 않는다 (사용자가 요청할 때만).
- 확신이 없거나 위험한 일(데이터셋 삭제, 대량 GPU 소비, 규칙 해석이 애매한 데이터 사용)은 하지 말고 리포트에 "사용자 확인 필요"로 적는다.

## 매 실행 절차
0. **지시와 점검 먼저**
   - `DIRECTIVES.md`를 읽는다. 사용자 지시는 여기 누적돼 있고, 이 매뉴얼보다 최신 지시가 우선한다.
   - `cd competitions/name-that-llm && uv run python src/health.py` → 경고 목록을 이번 실행의 우선 과제로 삼는다.
1. **상태 수집**
   - `kaggle competitions submissions name-that-llm` → 새로 나온 점수를 `EXPERIMENTS.md`의 해당 행 LB 칸에 기록 (pending → 점수). CV와의 차이도 메모.
   - 오늘(UTC 기준) 이미 쓴 제출 수 계산.
   - `kaggle competitions leaderboard name-that-llm -s` 상위권, 은·금 컷(상위 5%, 약 10+0.2% 순위) 점수 확인.
   - 실행 중인 내 커널 상태 (`kaggle kernels list --mine`, `kaggle kernels status`).
2. **판정**: 끝난 실험이 질문에 답했는지 `QUEUE.md`의 해당 항목에 결과와 결론을 적는다.
   - +0.010 이상만 개선으로 인정 (같은 코드 재제출 노이즈 ±0.009). 두 제출의 차이 sd ≈ sqrt(f/1200).
   - 풀로 학습한 모델은 CV가 LB보다 약 0.03~0.05 높다 (측정: lite -0.046, lite2 -0.034).
3. **제출**: `HYPOTHESES.md`의 "제출 운영 규칙"을 따른다. 제출 하나는 가설 하나의 시험이며, 시험할 가설이 없으면 한도를 남긴다 (남긴 한도는 경고 대상이 아님). 후보는 HYPOTHESES 우선순위 → `QUEUE.md` "다음 제출" 순.
   - 한 제출 = 변경 한 가지. 커널 디렉터리는 `kernels/<name>/`, 메타데이터는 private.
   - push → commit 완료 대기 → 로그 확인 (에러, sanity 체크) → `kaggle competitions submit name-that-llm -k mins00/<kernel> -v <ver> -f submission.parquet -m "<설명>"`.
   - 제출하면 `EXPERIMENTS.md`에 `| 날짜 | sNNN | 내용 | CV | pending | 메모 |` 한 줄 추가.
   - 21:10 실행에서는 남은 한도를 채점 시간을 고려해 쓴다 (다음 날 09:00 전에 채점 끝나지 않아도 괜찮음).
   - 공개 노트북 변형은 제출 전에 기준 노트북과 코드 셀 diff를 떠서 바뀐 인자를 EXPERIMENTS 메모에 적는다 (`kaggle kernels pull <ref> -m` 후 code 셀만 비교). 검토만 하고 재현하지 않은 노트북은 QUEUE "검토한 공개 노트북"에 이유와 함께 적는다 (health가 같은 경고를 반복하지 않도록).
   - 공개 노트북 diff는 코드 셀과 함께 `kernel-metadata.json`의 dataset/model/kernel_sources 차이도 본다. 새 소스(새 멤버)가 붙은 노트북이 손잡이만 바꾼 노트북보다 우선이며, 새 멤버는 '기준 + 멤버만' 한 가지 변경 제출로 효과를 분리한다.
   - 기준 후보가 채점 중이면 그 위 변형은 하루 2~3개까지만 내고 나머지 한도는 결과를 본 다음 실행으로 넘긴다.
   - 같은 종류의 변경(예: 후처리·가중 손잡이)이 연속 3회 노이즈(±0.009) 안이면 그 방향은 접고 QUEUE에 '종료'로 적는다. 이후 한도는 새 멤버·새 공개 파이프라인·로컬 CV 근거가 있는 변경에 쓴다.
4. **가설 실험** (남는 시간, 최대 약 2시간, 매 실행 최소 1건): `HYPOTHESES.md` 4절 순서대로 다음 가설의 검증을 진행해 CV를 측정하고 `EXPERIMENTS.md`와 HYPOTHESES 5절 검증 로그에 기록. 채택된 것만 "다음 제출"로 올린다. 긴 작업은 nohup으로 띄우고 다음 실행이 회수한다.
   - CV는 `src/cvlib.py` 하네스 (prompt_id GroupKFold, m2 컷)로만 측정.
   - 새 아이디어가 생기면 `QUEUE.md` 백로그에 추가.
5. **리포트**: `outputs/daily/report-YYYYMMDD-HHMM.md`에 한국어로 짧게:
   - 새 점수, 현재 best CV/LB, 순위와 메달 컷과의 거리
   - 오늘 제출한 것과 이유, 진행한 로컬 실험 결과
   - 문제나 사용자 확인이 필요한 일
   - `README.md`의 Best CV / LB 줄도 갱신.

6. **메커니즘 점검과 개선** (매 실행 마지막, 10분 이내)
   - 질문: 이번 실행이 점수를 올리는 데 실제로 기여했나? 한도를 낭비하거나, 같은 실패를 반복하거나, 기다리기만 한 곳이 있었나?
   - 점검: health 경고, 제출 한도 사용률, 지난 제출들의 판정 결과(개선 / 효과 없음 비율), 큐에 오래 머문 항목, 실패한 커널, 로그의 반복 실수.
   - 개선: 원인이 절차에 있으면 **이 매뉴얼, QUEUE.md, health.py를 직접 고친다**. 고친 내용은 아래 "변경 기록"에 한 줄 남긴다.
     - 절대 규칙은 고치지 않는다.
     - 사용자 판단이 필요한 것만 리포트의 "사용자 확인 필요"에 쓴다.
   - 리포트에 "메커니즘" 절을 둔다: 잘된 것 1개, 막힌 것 1개, 고친 것.
7. **주간 회고** (일요일 21:10 실행)
   - 한 주의 LB 추이, 실험 유형별 성과(무엇이 점수를 올렸나), 실패 패턴을 `outputs/daily/weekly-YYYYMMDD.md`에 쓴다.
   - 이를 바탕으로 큐의 우선순위를 다시 정하고, 성과 없는 방향을 정리한다.
   - 공개 노트북과 디스커션은 참고로만 조사한다. 우리 가설의 근거·반증이 되는 것만 HYPOTHESES.md에 반영한다.
